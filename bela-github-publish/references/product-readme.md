# 产品化 README

先根据读者要完成的任务决定内容。以下是可选骨架，不要求所有项目都有同样标题或模块。

## 首页的阅读路径

1. 产品名、一句具体用途；必要时一句适用场景。
2. 最短入口：在线体验、看效果、快速安装中的真实可用项。
3. 一张能代表当前产品的真实展示图或短动图，附清晰图注。
4. 按需求找能力：用“我想做什么 → 对应功能/入口 → 结果”组织；功能很多时用表格或可点击目录。
5. 第一次成功：一条能复制的请求或少量实际操作，写清输入、输出、从哪里看到结果。
6. 安装或开发入口：必要条件和真实命令；深入内容放独立文档。
7. 相关限制、验证状态、来源和许可。保留必要事实，不用未核实的泛化保证。

开头不要被环境清单、实现细节、兼容矩阵或更新日志占满。也不要为了简洁把必要依赖、真实限制或许可边界删掉。

## 根据交付类型调整

| 类型 | 优先展示 | 必须区分 |
| --- | --- | --- |
| 网页应用 | 可打开的体验链接、主要任务、真实界面 | 在线体验与本地开发；示例界面与真实业务服务 |
| Skill | 用户的一句话请求、输出结果、安装入口 | 文件安装、客户端加载/触发、完整功能实测 |
| 组件或代码库 | 可见效果、最小使用例、复用边界 | 原创代码、改写代码、素材、运行依赖的各自许可 |
| 多项目目录 | 按需求查找、分层目录、每项真实入口 | 项目清单与可安装包；没有机器消费者时不强行加协议或清单格式 |

## 截图如何选

- 先看已有成品，补主要能力的缺口；不为新 README 重做已确认视觉。
- 展示不同能力：文字、图片、控件、数据等应有可识别的差异，不反复截同一种布局。
- 截图来自可运行的当前版本，保留足够界面上下文，正文和主要视觉能读清；不含私人输入、账号信息或未获公开授权的素材。
- 图注用“这张图证明什么”来写，动效图注明静态不能展示完整节奏。需要证明运动时使用真实录制，不把关键帧拼图当录像。
- 在 GitHub 实际渲染后检查相对链接、图片加载和长代码换行；首页过长时用双列效果表或截图页分流。
